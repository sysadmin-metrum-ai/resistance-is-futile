## Section 1: Prerequisites (What Must Already Be Done)

**Headline:** Before You Run a Test Flight

**Body:**  
The following must already be complete. If not, complete them first (see the main venue-survey and location-map infographic prompts).

1. **Anchors placed** — Loco Positioning nodes are in their final positions and powered. Each anchor has clear line of sight to at least 3–4 others.
2. **Anchor positions calibrated** — Each anchor has been programmed with its 3D coordinates in NED (e.g. via `scripts/push-anchors.py` and an anchor file generated by drone-acharya with `--z-down`). The map is loaded into the anchors.
3. **Crazyflie ready** — At least one Crazyflie 2.x with a Loco Positioning deck is available. Crazyradio (USB dongle) is plugged into the same machine that will run the Drone API and the verify-position script.
4. **Python environment** — The project dependencies are installed with `uv sync`. The flight scripts and the backend (`src.main`) run in this environment.

**Visual suggestion:**

## Section 2: Step 1 — Start the Drone API (Backend)

**Headline:** Step 1: Start the Drone API

**Body:**  
The verify-position script does **not** talk to the Crazyflie directly. It sends commands (takeoff, go_to, land) and reads position through the **Drone API** (the FastAPI backend in this repo). So the backend must be running on the same machine (or on a host that the script can reach).

**Detailed steps:**

1. **Open a terminal** on the laptop that has the Crazyradio plugged in and the project checked out.
2. **Activate the project environment** (e.g. `source .venv/bin/activate` or `uv run`).
3. **Start the API server.** From the project root:
   ```text
   uv run uvicorn src.main:app --host 0.0.0.0 --port 8000
   ```
   Or, if the project uses a Makefile:
   ```text
   make run
   ```
   The server listens on port 8000. Leave this terminal running.
4. **Optional check:** In another terminal, run `curl http://localhost:8000/health` (or the project’s health endpoint). You should get a successful response. If the API is configured to require an **API key** (X-API-Key header), note the key; you may need to set it in the environment or pass it when calling the API (see project config).

**Visual suggestion:**  
Terminal window with the uvicorn (or `make run`) command. Callout: “Leave this running.” Second small callout: “Port 8000.”

## Section 3: Step 2 — Ensure Drone and Anchors Are Ready

**Headline:** Step 2: Drone and Anchors Ready

**Body:**  
Before running the test script, ensure the drone can be commanded and can see the anchors.

**Detailed steps:**

1. **Power on the Crazyflie** (battery or USB). Ensure the Loco Positioning deck is attached and the drone is bound to the same radio channel as the Crazyradio (e.g. 80, 2 Mbps). The backend (or the flight controller it uses) must be able to connect to the drone via the Crazyradio — see project docs for how drones are registered (e.g. by URI or ID).
2. **Power on all anchors** and confirm they are in range. The drone will get position from the Loco Positioning system; it needs to see at least 3–4 anchors.
3. **Confirm the drone is registered and idle.** If the API exposes a list of drones (e.g. `GET /drones`), you can check that your drone appears and is in an idle/available state. The verify-position script will use a **drone ID** (e.g. `drone-1` or `1` depending on API design — see script default and project docs). Ensure that ID matches a connected drone.
4. **Clear the flight area** — no people or obstacles in the path of the test pattern (e.g. a 1 m square or circle at 0.5 m height).

**Visual suggestion:**  
Simple diagram: Crazyradio → laptop; laptop → Drone API; Drone API → Crazyflie (radio); Crazyflie ↔ Anchors (UWB). Callout: “Drone sees 3–4+ anchors.”

## Section 4: Step 3 — Run the verify-position Script

**Headline:** Step 3: Run the Test Flight Script

**Body:**  
From a **second terminal** (with the API still running in the first), run the verify-position script. It will (1) call the API to take off, (2) command the drone to fly a pattern (e.g. square), (3) at each waypoint read the position reported by the Loco Positioning system, (4) return to origin and land, (5) compute the error between expected and actual positions and print a pass/fail result.

**Detailed steps:**

1. **Open a new terminal**; activate the same project environment; `cd` to the project root.
2. **Run the script** with at least pattern, size, and threshold. Example (square, 1 m side, 20 cm threshold):
   ```text
   python scripts/verify-position.py --pattern square --size 1.0 --threshold 0.2
   ```
3. **Optional arguments (must appear on infographic):**
   - `--pattern` — `square`, `circle`, or `figure8` (default: square).
   - `--size` — For square: side length in meters; for circle: radius in meters; for figure8: scale (default: 1.0).
   - `--height` — Flight altitude in meters (default: 0.5).
   - `--threshold` — Pass/fail threshold in meters; test passes if RMS error ≤ this (default: 0.2 = 20 cm).
   - `--drone` — Drone ID used by the API (default: `drone-1`). Must match a connected drone.
   - `--api` — Base URL of the Drone API (default: `http://localhost:8000`). Use this if the API runs on another host.
   - `--verbose` or `-v` — Print waypoint-by-waypoint details.
   - `--dry-run` — Generate waypoints only; do not fly (useful to check pattern and coordinates).
4. **Watch the script output.** It will print progress (takeoff, waypoints, landing) and at the end a **POSITIONING VERIFICATION RESULTS** block with RMS error, max error, and PASSED or FAILED.

**Visual suggestion:**  
Second terminal with the full command:  
`python scripts/verify-position.py --pattern square --size 1.0 --threshold 0.2`  
Below it, a small table of options (pattern, size, height, threshold, drone, api, verbose, dry-run). Optional: simple flow “Takeoff → Fly pattern → Record positions → Land → Compare → Pass/Fail”.

## Section 5: Step 4 — Interpret Results

**Headline:** Step 4: Interpret the Results

**Body:**  
The script prints a results block and exits with code 0 (passed) or 1 (failed).

- **RMS Error** — Root-mean-square of the position errors at each waypoint (in meters). Lower is better.
- **Max Error** — Largest error at any single waypoint (in meters).
- **Pass/Fail** — **PASSED** if RMS error ≤ the threshold you set (e.g. 0.2 m = 20 cm). **FAILED** otherwise.

**What to do:**

- **PASSED** — Positioning is within the accepted tolerance. You can proceed to missions or demos. Optionally run again with a different pattern (e.g. circle) or larger size to gain confidence.
- **FAILED** — RMS error exceeds the threshold. Check: (1) Anchor positions correct? Re-run push-anchors if needed. (2) Drone sees 3–4+ anchors throughout the path? (3) Interference (metal, people)? (4) Try a smaller pattern or lower height. See venue-survey troubleshooting (anchor coverage, re-measure).

**Exit code:** The script exits 0 on pass, 1 on fail so you can use it in scripts or CI (e.g. `scripts/verify-position.py ... && echo "OK"`).

**Visual suggestion:**  
Example results block (short): “RMS Error: 12.34 cm … RESULT: PASSED”. Next to it: “Exit 0 = pass, Exit 1 = fail.” Small “If FAILED” checklist: anchors correct? coverage? interference? smaller pattern?

## Section 6: Quick Reference — Commands and Options

**Headline:** Quick Reference

**Body (distill to a compact reference on the graphic):**

**Start API (Terminal 1):**
```text
uv run uvicorn src.main:app --host 0.0.0.0 --port 8000
```

**Run test flight (Terminal 2):**

**Common options:**

| Option | Meaning | Default |
|--------|---------|---------|
| `--pattern` | square, circle, figure8 | square |
| `--size` | Side (square), radius (circle), scale (figure8) in m | 1.0 |
| `--height` | Flight altitude (m) | 0.5 |
| `--threshold` | Pass if RMS error ≤ this (m) | 0.2 |
| `--drone` | Drone ID for API | drone-1 |
| `--api` | API base URL | http://localhost:8000 |
| `--verbose` / `-v` | Verbose output | off |
| `--dry-run` | No flight, print waypoints only | off |

## Section 7: Troubleshooting (Optional Callout)

**Headline:** If Something Goes Wrong

**Body:**  
- **“Cannot connect to drone”** — API running? Drone powered and connected via Crazyradio? Drone ID (e.g. `--drone`) correct? Check API docs for how drones are registered.
- **401 Unauthorized** — API may require an X-API-Key header. Check project config (e.g. `.env`, `API_KEY`); the script may need to send this header (see project docs).
- **Large position errors or FAILED** — See “Step 4: Interpret Results” (anchors, coverage, interference). Re-verify anchor positions and run push-anchors if needed.
- **Drone does not move** — Backend and flight controller must be wired to the same Crazyradio and drone URI; see project architecture (e.g. MissionQueue, FlightController, cflib).

**Visual suggestion:**  
Small “Troubleshoot” box with four bullets (connection, 401, large errors, drone not moving) and “See project docs / venue-survey procedure.”
